## 通用约定

默认使用同源相对路径。前后端分端口或分域部署时，在 `.env.local` 中设置 `NEXT_PUBLIC_API_BASE_URL`，同时由后端正确配置 CORS。

**请求。** `POST` 的请求体是 JSON，`Content-Type: application/json`。

**响应。** 前端只看 `res.ok`，非 2xx 直接抛错并把错误信息显示在该页面的提示位 + 弹 toast。**不会白屏。**

**会话。** 所有写操作都带 `sessionId`，由前端 `crypto.randomUUID()` 生成，页面刷新即换新。

**失败的表现。** 接口失败时前端降级而不是崩：

| 失败位置 | 前端表现 |
| --- | --- |
| 课时详情 | 课程卡显示「载入失败」+ 原因，开始按钮保持禁用 |
| 教学视频 | 播放器显示「接口待接入」占位 |
| 其他 | 弹 toast，停留在当前阶段 |

### ① 课时详情

```
GET /api/lesson?lessonId=ch3-process-scheduling
```

```jsonc
{
  "ok": true,
  "lesson": {
    "lessonId": "ch3-process-scheduling",
    "course": "操作系统",
    "chapter": "第 3 章",
    "title": "处理机调度",
    "summary": "CPU 一次只能服务一个进程……",
    "knowledgePointCount": 6,
    "segmentCount": 6,
    "estimatedMinutes": 45,
    "knowledgePoints": ["调度是什么", "三级调度", "..."],
    "segments": [
      {
        "segmentId": "seg-001",
        "title": "调度是什么、为什么需要调度",
        "order": 1,
        "startSeconds": 750,     // 在整条教学视频上的起始秒数
        "endSeconds": 1080
      }
    ]
  }
}
```

`segments` 用于「从第一个片段的位置开始播视频」，以及未来做片段跳转。

### ② AI 对话

```
POST /api/chat
← { sessionId, lessonId, message, now }
```

```jsonc
{
  "ok": true,
  "message": { "text": "……", "speech": "" },   // speech 可留空
  "hostPhase": "intro",        // 见下表
  "introComplete": false
}
```

#### `hostPhase` —— 前端唯一跟随的字段

取值与 `ORCHESTRATOR.md` §2 一致，**七个**：

| hostPhase | 前端显示哪个界面 | 状态胶囊文字 |
| --- | --- | --- |
| `uninitialized` | 课前（课时卡） | 课前 |
| `intro` | 对话 | 课程介绍 |
| `guided_learning` | 对话 + 视频 | 引导学习 |
| `recap_discussion` | 写作区 + 反馈 | 总结复述 |
| `deep_inquiry` | 三张卡 | 深入思考 |
| `class_discussion` | 讨论区 | 课堂讨论 |
| `ending` | 结束态 | 已结束 |

**前端完全不参与「该不该切幕」的判断。** 每次响应回来后比对 `hostPhase`：
变了就切界面（并播一次过渡），没变就什么都不做。切幕时机由后端的
`judge_advance` 决定（真实时钟 + 证据 + 策略，见 `ORCHESTRATOR.md` §6）。

> ⚠️ 老版本的 `lecturing` / `segment_summary` / `point_review` / `post_class`
> **已废弃**，前端认不出来会忽略（只在控制台留一条警告，不会崩）。
>
> ⚠️ 后端若下发前端不认识的新 phase，同样会被忽略 —— 所以后端加新阶段时，
> 老前端不会中断，只是少显示一幕。

#### `introComplete`

表示「课程介绍讲完，可以放视频了」。前端据此显示「开始播放教学视频」按钮。

`guided_learning` 内部还有「对话 / 视频」两段，那是前端的局部状态，
不由 `hostPhase` 区分 —— 学生在对话页点按钮进入视频页，不经过后端。

#### 控制消息

学生有几个动作不是「一轮对话」，约定成以 `/` 开头的消息，走同一个通道：

| 消息 | 什么时候发 | 期望的后端行为 |
| --- | --- | --- |
| `/上课开始` | 学生点「开始上课」 | 进 `intro`，返回课程介绍 |
| `/视频结束` | 视频自然播完，**或**学生点「看完了，继续」 | 进 `recap_discussion` |
| `/继续` | 学生点「进入下一阶段」（手动推进） | 由 `judge_advance` 判定是否推进 |
| `/下课` | 学生点「结束本节课」 | 进 `ending`，返回老师的收尾发言 |

后端的 `classify_turn` 需要识别这几条。**「学生手动进入下一阶段」保留着，
但推不推由后端决定** —— 前端只负责发请求、然后跟随 `hostPhase`。

#### `now` —— 前端注入的时间戳

请求体里的 `now` 是 ISO8601 时间戳（如 `2026-09-18T14:30:00.000Z`）。

`ORCHESTRATOR.md` §2 说 `now` 由「会话层」注入、图内节点不得自己取时间。
前端先按 ISO8601 带上，**用不用由后端决定**（真实时钟由后端结算更可靠）。

#### `sessionId` 的语义

它是后端 checkpointer 的 `thread_id`（`ORCHESTRATOR.md` §7）。前端已改成
**持久化存储**（`localStorage`），刷新页面沿用同一个 —— 这样后端才能从
上一轮状态恢复。**后端不要用它之外的东西做会话标识。**

### ③ 教学视频

```
GET /api/lesson/video?lessonId=ch3-process-scheduling
```

```jsonc
{
  "ok": true,
  "video": {
    "url": "https://...",     // mp4 / HLS
    "poster": "",             // 封面，可空
    "duration": 2700,         // 总时长（秒）
    "title": "处理机调度",
    "source": "openmaic"      // 'openmaic' | 'manual'
  }
}
```

返回 `null` 或不带 `url` 时，前端显示占位，不报错。

> **按「整节课一条视频」建模。** `lesson.segments[].startSeconds` 是它上面的时间点，播放某个片段就是 seek 过去。这个模型来自后端 `segment.source.position` 的写法（如 `"视频进度占位 00:12:30"`）。
>
> 教师端 openmaic 有 `/api/export-video/*` 能力，学生端届时经平台接口取已发布的成片地址。

### ⑤ 阶段 2：提交复述，拿结构化反馈

```
POST /api/summary/review
← { sessionId, lessonId, segmentId, text }
```

```jsonc
{
  "ok": true,
  "review": {
    "strengths":   ["你抓住了核心矛盾：……"],       // 讲对的
    "gaps":        ["没有提到三级调度的区分……"],     // 遗漏的
    "supplements": ["补一点：调度不只是「选谁」……"], // 补充
    "connections": [                                // 和以前内容的关联
      { "lesson": "第 2 章 进程管理", "note": "进程五状态里「就绪 → 运行」……" }
    ]
  }
}
```

四块分别渲染成四张不同颜色的卡（绿 / 橙 / 蓝 / 紫）。**任何一块为空数组都会被跳过**，不会渲染空卡。

`text` 是学生写的复述原文，前端限制 600 字。

### ⑥ 阶段 3：提交思考，拿点评

```
POST /api/reflection
← { sessionId, lessonId, lens, answer }
```

`lens` 取三个值之一，对应三张卡片：

| lens | 卡片标题 | 题目（前端当前写死在 `REFLECTION_LENSES`） |
| --- | --- | --- |
| `logic` | 底层逻辑 | 为什么要调度，而不是让每个进程一直运行到结束？ |
| `application` | 实际问题 | 这套调度机制，能解决现实中的哪些问题？ |
| `transfer` | 跨学科关联 | 它和其他学科有什么关联？ |

```jsonc
{
  "ok": true,
  "critique": {
    "verdict": "good",       // 'good' | 'partial' | 'shallow'
    "comment": "方向对了。**不能一直运行到结束**是关键……",   // 可含 **粗体**
    "followUp": "如果 CPU 有 8 个核心，调度还需要吗？"        // 「再想一层」，可空
  }
}
```

`verdict` 决定点评卡的配色和标题文案。`comment` 支持 `**粗体**`（前端先转义再解析，不会 XSS）。

> 题目目前写在前端（内容取自后端的 `KNOWLEDGE-BASE.md`）。若改由后端下发，只需改 `REFLECTION_LENSES` 这一处。

### ⑦ 阶段 4：讨论流

**取讨论流**

```
GET /api/discussion?lessonId=ch3-process-scheduling
```

```jsonc
{
  "ok": true,
  "topic": "如果你是操作系统设计者，面对「交互式任务和批处理任务混跑」的场景……",
  "messages": [
    { "id": "d1", "speaker": "host", "name": "老师",   "text": "……", "at": "14:32" },
    { "id": "d2", "speaker": "peer", "name": "林知遥", "text": "……", "at": "14:33" }
  ]
}
```

`speaker` 取 `host` / `peer` / `me`，决定气泡的配色和头像：

| speaker | 头像 | 气泡 |
| --- | --- | --- |
| `host` | 紫色，首字「师」 | 淡紫 |
| `peer` | 灰色，姓名首字 | 浅灰 |
| `me` | 无 | 蓝色，右对齐 |

**提交发言**

```
POST /api/discussion
← { sessionId, lessonId, text }
→ { ok, message: { id, speaker: "me", name: "我", text, at } }
```

**老师收尾**

```
GET /api/discussion/end?lessonId=ch3-process-scheduling
→ { ok, closing: "时间到了，今天就到这里。……" }
```

> **目前是 pull 模型**：进入阶段 4 拉一次全量，学生发言后本地追加，老师的追问由前端 mock。
> 真实多人讨论需要换成长连接（SSE / WebSocket）或轮询 —— 届时只需替换 `src/legacy/stage-discuss.js` 里的取数逻辑，界面不用动。

## 后端需要补齐的工作

以 `ORCHESTRATOR.md` 的目标结构为准。**前端只依赖下面这几条**：

**1. `/api/chat` 下发 `hostPhase`** —— 最关键的一条
前端完全跟随它切界面。没有这个字段，前端就一直停在课前。
取值必须是 `ORCHESTRATOR.md` §2 的那七个。

**2. `classify_turn` 要能识别四条控制消息**（见 ② AI 对话）
`/上课开始`、`/视频结束`、`/继续`、`/下课`。
学生的这些动作不是自然语言，是约定的动作。

**3. 切幕逻辑按真实时钟走**（`ORCHESTRATOR.md` §5–6）
`tick` 结算真实耗时，`judge_advance` 按预算 + 证据 + 策略判定。
**前端不参与这个判断** —— 它只负责把结果显示出来。

**4. `session_id` 作为 checkpointer 的 `thread_id`**（§7）
前端已改成持久化存储，刷新沿用同一个。后端需要按它存状态。

**5. 阶段内容（`stages/`）可以先空壳**
`ORCHESTRATOR.md` §8 明确写了空壳的降级行为 —— **内容为空不影响开课**。
所以前端可以先把链路跑通，内容后补。

### 前端目前不依赖、但迟早要对的

**掌握度**（`mastery_updates`）
`ORCHESTRATOR.md` §2 里的 `mastery_updates: [{kp_id, old_stars, new_stars, source, evidence, stage}]`
是掌握度的写入通道。前端**暂时不展示**，但接口位置留着了 ——
响应里带了这个字段就能直接用，不用改后端。

注意封顶规则：课内答疑最高 4 星，**5 星只能由正式考核产生**。

**多学生**（阶段 4 的讨论）
后端 `student_id` 目前全链路硬编码，没有班级 / 花名册 / 讨论组任何结构。
前端阶段 4 的老师和同学发言全是前端 mock，真实多人讨论需要长连接（SSE / WebSocket）或轮询。

## 将来加多门课时的接口

现在只有一节课（`LESSON_ID = "ch3-process-scheduling"`），所以入口不提供选课。要扩成「选课程 → 课堂 / 课后」两级结构时，需要以下三个接口：

```
GET /api/courses
→ { ok, courses: [{
      courseId, name, summary,
      lessonCount, completedLessonCount,
      status: 'not_started' | 'in_progress' | 'completed',
      currentLessonId, currentLessonTitle,     // 当前要上的那一节
      progress: { completedPhases, masteryAvg, lastActiveAt }
    }] }
```

```
GET /api/courses/<courseId>
→ { ok, course: { ...同上... } }
```

```
GET /api/courses/<courseId>/lessons
→ { ok, lessons: [{
      lessonId, chapter, title, summary,
      knowledgePointCount, segmentCount, estimatedMinutes,
      status, progress: { currentStage, completedPhases, masteryAvg }
    }] }
```

同一份契约也记在 `src/legacy/api.js` 文件末尾。
